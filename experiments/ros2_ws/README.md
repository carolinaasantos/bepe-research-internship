## Division

This README is divided into:
1. Experiments: ROS2 Controller
2. Experiments: ROS2 Launch file

# 1. Controller

## Overview

This ROS2 node executes multi-robot trajectories generated by a MAPF planner such as **ICBS** or **RHCR**. Each robot loads its assigned path, navigates through a sequence of waypoints, performs payload handling actions, and optionally synchronizes with other robots during execution. When unarmed, the controller does not publish `cmd_vel`, allowing the standard joystick teleoperation stack to control the robot. This is used to verify motor and wheel operation before starting an experiment. Once validated, the controller can be armed to begin MAPF execution.

The controller integrates:

* Trajectory execution
* Localization monitoring
* Heading stabilization
* ICBS synchronization barriers
* Lifter control
* Data logging and telemetry

## Input Data

The `instances` folder is copied from the VRPPD solver directory to the ROS2 workspace (specifically within directory `dots_templates/src/dots_example_controllers/dots_example_controllers`). The controller loads a trajectory file generated by the MAPF stage depending on the chosen algorithm:

* ICBS: `*_icbs_converted_paths.txt`
* RHCR: `*_rhcr_converted_paths.txt`

File format:

```text
agent_id
x1 y1 x2 y2 ...
x1 y1 x2 y2 ...

next_agent_id
x1 y1 x2 y2 ...
x1 y1 x2 y2 ...

...
```

In which (x1,y1) represents a waypoint. Each agent contains one or more trajectory segments. The last waypoint of a segment represents a goal location.

Example:

```text
0
0 0 1 0 2 0
2 0 2 1 2 2

1
6 6 5 6 4 6
4 3 2 1 5 5
```

## Robot Identification

Each physical robot is automatically mapped to a MAPF agent ID through its hostname:

```python
HOSTNAME_TO_AGENT_ID = {
    "robot_xxxxxxxx": 0,
    "robot_yyyyyyyy": 1,
    "robot_zzzzzzzz": 2,
}
```

This allows the same controller to run on multiple robots while assigning different trajectories.

## Navigation Strategy

This controller is responsible only for executing waypoint trajectories that were previously generated by the planning pipeline.

Responsibilities are divided as follows:

| Component | Responsibility |
|------------|---------------|
| VRPPD Solver | Assign pickup and delivery tasks to robots |
| MAPF Planner (ICBS/RHCR) | Generate collision-free paths for each robot |
| Localization Stack (EKF, Odometry, ArUco) | Estimate robot pose |
| Trajectory Controller (this node) | Track waypoints and generate velocity commands |
| Robot Base Controller | Execute velocity commands on the hardware |

The controller receives a sequence of waypoints and performs local trajectory tracking.

For each waypoint:

1. Compute the position error relative to the current robot pose.
2. Generate a velocity command toward the target waypoint.
3. Transform the command from the world frame into the robot body frame.
4. Maintain a fixed heading using a proportional yaw controller.
5. Advance to the next waypoint once the target is reached.

The controller does not perform global path planning or task allocation. Those steps are completed beforehand by the VRPPD and MAPF modules.

A waypoint is considered reached only after remaining within a configurable distance threshold for several consecutive control cycles.

## ICBS Synchronization

When operating in **ICBS mode**, robots synchronize at every goal location.

Synchronization procedure:

```text
Reach goal
    ↓
Stop robot
    ↓
Publish completion counter
    ↓
Wait for all robots
    ↓
Hold position
    ↓
Proceed to next goal
```

This guarantees that all robots execute the MAPF schedule consistently.

In **RHCR mode**, synchronization is already implemented within the MAPF algorithm and robots proceed immediately to the next goal.

## Lifter Control

The controller automatically actuates the robot lifter at goal locations.

Behavior:

* Odd-numbered goals → Lifter UP
* Even-numbered goals → Lifter DOWN

## Localization Sources

The controller monitors multiple localization sources:

* EKF filtered odometry
* Raw wheel odometry
* ArUco marker localization

Before trajectory execution begins:

1. At least one ArUco detection must be received (even though the minimum quantity to guarantee a good location is 3 markers).
2. The operator arms the robot.
3. The EKF is allowed to settle for a configurable period.

The localization workflow is:

Wheel Odometry
    ↓
   EKF ← ArUco Localization
    ↓
Odometry/filtered
    ↓
Trajectory Controller

### Wheel Odometry

The robot continuously estimates its motion using wheel encoder measurements. This provides smooth short-term motion estimation but accumulates drift over time.

Published topic:

`odom`

### ArUco Localization

An onboard camera detects ArUco markers placed in the environment.

From these detections, the system computes an absolute robot pose estimate relative to the arena reference frame.

Published topic:

`cam_aruco_odom`

ArUco measurements provide global corrections that help compensate for wheel-odometry drift.

### Extended Kalman Filter (EKF)

The EKF fuses:

Wheel odometry
ArUco pose estimates

to produce a more robust and stable localization estimate.

Published topic:

`odometry/filtered`

This filtered pose is the primary localization source used by the trajectory controller during waypoint tracking.

## Data Logging

Execution data is continuously recorded to CSV files.

Logged information includes:

* Robot position
* Target waypoint
* Velocity commands
* Obstacle distances
* Lifter state
* Goal progress
* ArUco measurements

Example output:

```text
time,goal_index,wp_index,target_x,target_y,
filtered_x,filtered_y,filtered_yaw,
cmd_vx,cmd_vy
```

## Telemetry

Runtime statistics are optionally exported to InfluxDB.

Available metrics include:

* Current goal and waypoint
* Robot position
* Commanded velocities
* Obstacle distances
* Lifter state
* Localization status

These metrics can be visualized in dashboards such as Grafana.

## Execution Workflow

```text
Load MAPF trajectory
    ↓
Assign trajectory to robot
    ↓
Wait for ArUco localization
    ↓
Operator arms robot
    ↓
EKF settling period
    ↓
Follow waypoints
    ↓
Reach goal
    ↓
(If ICBS) ICBS synchronization
    ↓
Actuate lifter
    ↓
Proceed to next goal
    ↓
Finish trajectory
```

# 2. Launch

## Overview

This launch file starts the complete software stack required to execute MAPF trajectories on a physical robot.

The launch combines:

* Localization system (camera, ArUco, and EKF)
* MAPF trajectory controller
* Robot-specific configuration

The controller executes trajectories previously generated by the VRPPD and MAPF planning stages.

## Components

### Localization Stack

The launch includes:

```text
basic_cam_ekf.launch.py
```
Which starts the complete localization pipeline used by the trajectory controller. The stack combines:

* Wheel odometry
* Camera acquisition
* ArUco marker detection
* Extended Kalman Filter (EKF)

The trajectory controller relies on these localization sources to track waypoints accurately.

### MAPF Trajectory Controller

The launch starts:

```text
mapf_trajectory
```

This node:

* Loads the robot's assigned trajectory
* Follows MAPF-generated waypoints
* Performs ICBS synchronization when enabled
* Controls the robot lifter
* Logs execution data to CSV files

The controller does not perform task allocation or path planning. It only executes trajectories generated offline.

## Robot Identification

By default, the launch automatically determines the robot name from the machine hostname.

Example:

```text
robot_31c4efef
robot_b6bd40d3
robot_e213b058
```

## Launch Parameters

- **use_sim_time**  
  Enables ROS simulation time.  

- **robot_name**  
  ROS namespace for the robot.  

- **speed**  
  Maximum trajectory tracking speed.  

- **dwell**  
  Number of consecutive control cycles required to confirm waypoint arrival.  

- **robot_id**  
  MAPF agent identifier.

## Usage

```bash
ros2 launch dots_example_controllers mapf_trajectory.launch.py
```

This launch file is responsible only for starting the execution stack. Route generation and conflict resolution are performed beforehand by the VRPPD and MAPF modules.
